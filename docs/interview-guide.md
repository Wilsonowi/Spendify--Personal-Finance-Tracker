# Interview Guide

## Sixty-Second Pitch

Spendify solves a data-correctness problem in personal finance. It imports
Public Bank and TNG monthly statements, validates the complete PDF, posts sound
rows automatically with provisional categories where needed, and isolates only
genuine accounting exceptions. It also
reconciles bank-to-wallet top-ups so moving RM100 does not become RM200 of fake
spending. The Java and Spring Boot backend uses PostgreSQL constraints,
encrypted MinIO storage, and isolated PaddleOCR for single slips. The React PWA
opens the latest closed month with net spending, refunds, categories, merchants,
coverage, and transfers.

## Questions To Expect

**Why PostgreSQL instead of Firestore?**

Transactions, transfer pairs, category rules, and budgets benefit from foreign
keys, exact decimal types, partial unique indexes, and transactional updates.

**Why not classify everything with an LLM?**

Finance needs repeatability. Confirmed private aliases run first, then seeded
rules. AI is only a confidence-scored fallback using sanitized merchant text.

**How is a transfer detected?**

Candidates require equal amounts, opposite directions, a bank/eWallet account
pair, top-up evidence, and a valid time window. A unique candidate is confirmed
automatically; ambiguity stays reviewable. SQL constraints enforce one-to-one
confirmed links.

**Why does statement import not use OCR?**

Digital statements already contain structured text. PDFBox is faster and more
deterministic, avoids recognition errors, and keeps names and account headers
local. Scanned PDFs fail clearly instead of producing a low-trust ledger.

**Why a modular monolith?**

The workload deploys as one product and does not need independent business
scaling. One OCR sidecar is justified by the Python model ecosystem. Additional
message infrastructure would add failure modes without improving the use case.

**What prevents duplicate spending?**

SHA-256 rejects the same source file. Strong row duplicates require the same
privacy-safe provider-reference fingerprint, account, date, amount, direction,
and type. Different references remain separate, opposite directions can never
be duplicates, and weak evidence is held for review.

**How are documents protected?**

Every file has a random data key and GCM nonce. Ciphertext is stored in MinIO,
the data key is wrapped by an external master key, and authorization occurs
before streaming decryption.

## SQL Topics Demonstrated

- Normalized ownership and finance relationships.
- `NUMERIC(14,2)` money values and check constraints.
- Composite, partial unique, and time-oriented indexes.
- Foreign-key deletion behavior.
- Flyway migrations and transaction boundaries.
- One encrypted source document mapped to ordered statement rows with unique
  source sequences and explicit resolution progress.
- Period-based aggregation and exclusion of internal transfers.

## Verified Evidence To Show

- `PostgresContractTest` starts PostgreSQL 18 with Testcontainers and checks
  Flyway, `NUMERIC(14,2)`, constraints, indexes, ownership-scoped repositories,
  and one-to-one transfer enforcement.
- `golden_check.py` runs real PP-OCRv6 inference over synthetic Public Bank and
  TNG images and checks expected tokens and confidence.
- `workspace.spec.ts` drives the complete Compose stack and proves RM100 is an
  internal transfer while RM12.50 remains the only monthly expense.
- `statement-workflow.spec.ts` proves automatic posting with provisional
  categories, source coverage, category-quality reporting, and date-only
  reconciliation.
- `docs/screenshots/dashboard-real.png` and
  `docs/demo/spendify-real-demo.webm` are generated by that real workflow, not
  mocked data or personal financial records.

When demonstrating, distinguish three levels of testing: deterministic unit
tests for business rules, container-backed database/OCR contracts, and one
browser workflow that validates the assembled system.

## Improvements After Version One

- Additional provider adapters and CSV import.
- Key rotation backed by a dedicated KMS.
- Stronger job claiming for multi-instance processing.
- Recurring-payment detection after sufficient history exists.
- Public demo mode restricted to synthetic fixtures.
